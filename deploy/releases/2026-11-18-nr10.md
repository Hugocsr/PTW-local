## Pendências constatadas no ambiente hospedado

1. O Supabase utiliza PostgreSQL 17.11. O esquema `ptw` existe, mas **não possui `permit_revalidation` nem `permit_revalidate`**. O código novo não deve ser publicado apontando para esse esquema anterior.
2. A consulta encontrou zero PTs, mas isso não autoriza apagar cadastros, modelos ou auditoria existentes. Fazer backup e ensaio de restauração antes de qualquer troca.
3. A Vercel mantém host, usuário, pool e CA do banco com overrides para a branch **`ptw-sgi`**. Uma branch nova não herda esses overrides. A branch de produção configurada é `main`.
4. Login de homologação `PTW_LDAP_MODE=preview` só é aceito em Preview. As variáveis verificadas estão no ambiente Preview. Não promover esta configuração para Production.
5. Os dois modelos, os locais, ativos, cargos, pessoas e vínculos do laboratório são dados persistidos. **Git e Dockerfile não transportam esses registros.** O LDAP de Preview atual também não deve ser presumido como equivalente ao diretório completo do Docker local.

## Ordem para concluir a publicação

### 1. Banco e armazenamento

- Redigir/refinar/validar a spec de atualização hospedada: destino, preservação de cadastros/modelos/auditoria, usuários de teste e reversão. A preparação não implementa novas regras de negócio.
- Capturar backup do esquema/dados `ptw` e inventário dos anexos; conferir restauração em destino isolado. Preservar IDs, referências e cadeia de auditoria. Não copiar o banco fictício local sobre o remoto existente.
- Preparar o esquema final em destino vazio compatível com PostgreSQL 17, usando a adaptação existente `ptw-server/tools/schema_supabase.mjs`. Esse gerador produz um **bootstrap para destino vazio**, não uma atualização incremental. Não executá-lo sobre o esquema atual.
- Restaurar e conferir os dados necessários no destino candidato antes de habilitar gatilhos finais, conforme ensaio aprovado. O projeto mantém o esquema canônico como fonte; não criar uma cadeia de migrações ad hoc.
- Conferir RLS, papel da API, permissões, CA e conexão que preserve sessão para LISTEN. Não ampliar acesso de `anon`/`authenticated` ao esquema privado para resolver um erro da API.
- Executar `deploy/releases/nr10-preflight.sql` no candidato e exigir `ready=true`. O preflight verifica a presença de estruturas e controles principais; ainda são necessários hashes, ensaios e fluxo completo.
- Só apontar o Preview para o destino candidato depois das conferências; manter o destino anterior disponível para reversão.

### 2. Código no GitHub

Usar o terminal da conta Windows autenticada no GitHub. Na raiz do checkout preparado, depois da revisão do commit:

```powershell
git -c "safe.directory=$((Get-Location).Path.Replace('\','/'))" fetch origin ptw-sgi
git -c "safe.directory=$((Get-Location).Path.Replace('\','/'))" merge-base --is-ancestor origin/ptw-sgi HEAD
```

Se o segundo comando retornar erro, parar e reconciliar os commits remotos; não usar force push. Se não houver divergência **e o banco candidato estiver pronto**, publicar no destino Preview:

```powershell
git -c "safe.directory=$((Get-Location).Path.Replace('\','/'))" push origin HEAD:refs/heads/ptw-sgi
```

O push pode iniciar automaticamente um deploy pela integração Git. Não publicar na `main`: ela é a branch de Production, e esta entrega usa LDAP/variáveis de Preview. Uma nova branch de Preview só pode ser usada após configurar os mesmos overrides de ambiente nela.

### 3. Deploy na Vercel

- Abrir o projeto **ptw**, conferir a origem `ptw-sgi` e o SHA do commit preparado.
- Conferir runtime Container, raiz `.` e `Dockerfile.vercel`; não usar build `demo-public` nem publicar somente `dist`.
- Conferir em Preview: `PTW_UNIT`, banco/usuário/senha/CA/pool, S3 e credenciais, `PTW_LDAP_MODE` e senha de Preview. Não incluir valores no Git, em screenshots ou neste roteiro.
- Aguardar o deploy do commit novo. Se for preciso redeploy, selecionar o deploy desse commit; redeploy de um commit antigo não traz as alterações novas.
- Conferir `/api/v1/health`, login e leitura do cadastro. Health isolado não comprova compatibilidade do banco.

### 4. Dados e aceite ponta a ponta

- Exportar os dois modelos locais pelo recurso de exportação `ptw.modelo/1`; importar na homologação, revisar os cargos/referências e ativar versões separadas. Não alterar modelos já usados por PTs históricas.
- Cadastrar/importar locais, ativos e subconjuntos fictícios; conferir escopo dos cargos e pessoas. Definir na spec os usuários e a segregação de assinaturas do Preview: o roteiro local exige mais pessoas do que o login único atual de homologação.
- Executar os dois roteiros manuais com identidades autorizadas e a API/banco/S3 hospedados, inclusive anexos, recusas, parada/retomada, novo aceite, revalidação por turno, entrega e encerramento.
- Conferir impressão, histórico, integridade dos anexos e auditoria. Validar a versão do modelo preservada após recarregar e após novo deploy.
- Só declarar o ambiente publicado e funcional após esses testes. Registrar URL, SHA, hashes do esquema e evidências de execução.
